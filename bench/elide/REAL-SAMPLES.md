# Barrier elision on real samples: measuring on a GPU (Windows)

This part runs **unmodified** SaschaWillems/Vulkan and KhronosGroup/Vulkan-Samples programs with
and without the COVENANT elision plans proved on the model driver. The plan-level results are in
`real/results/real.md` (generated by `real/run_real.py`): on these expert-written samples the
plans change **no per-frame barrier**; they only narrow some one-time setup barriers. A GPU
run therefore has three purposes:

1. confirm on real hardware that loading the plans changes nothing: identical images, no new
   syncval hazards;
2. measure what the elide layer costs by itself;
3. supply a null control: real samples should give 0%, while the microbenchmarks in
   `bench/elide` give 2–24%.

**Do not report a plan/base difference as a speedup when the table marks the row "plan changes
nothing per frame".** The difference is noise or layer overhead.

Files:

| file | what |
|---|---|
| `bench/elide/real/plans/<app>_<sample>.f2.plan.json` | plans proved from the 2-queue-family traces (for GPUs with a dedicated compute family, such as current NVIDIA GPUs); `.report.json` next to each |
| `bench/elide/real/CMakeLists.txt` | builds both layers (MSVC or MinGW-w64) |
| `bench/elide/real/measure_real.py` | runs the samples in interleaved base / off / plan order, using probe timestamps and image hashes |
| `elide_layer/` | VK_LAYER_COVENANT_elide (source) |
| `bench/elide/real/probe_layer/` | VK_LAYER_COVENANT_probe: per-batch GPU timestamps and presented-image hashes |

## 0. Prerequisites

Install:

- the NVIDIA driver;
- the LunarG Vulkan SDK, 1.4.x (it includes the loader at 1.3.234 or newer, which `VK_ADD_LAYER_PATH` needs, plus the validation layer and glslc);
- Git;
- Python 3;
- CMake 3.20 or newer;
- for MSVC: Visual Studio 2022 or its Build Tools, with "Desktop development with C++".

For MinGW-w64, use MSYS2 UCRT64 (`pacman -S mingw-w64-ucrt-x86_64-toolchain mingw-w64-ucrt-x86_64-cmake`)
or w64devkit. Only the two layers have a MinGW path here. Build the samples with MSVC: Vulkan-Samples
supports only MSVC on Windows, and Sascha's samples have not been tried with MinGW. The layers may
use a different compiler from the application, because the loader loads them by C ABI.

Prepare the machine as in `bench/elide/README.md` (Windows section, step 4):

- power mode "Best performance", on AC power;
- NVIDIA "Prefer maximum performance";
- write down the hardware-accelerated GPU scheduling setting.

Run everything from a normal **non-administrator** prompt. The loader ignores layer-path variables
in elevated processes.

Vulkan-Samples' build docs ask for Developer Mode, or an administrator prompt, for running
samples (symlinks). Turn on Developer Mode (Settings → System → For developers) so the samples
run from a non-administrator prompt.

## 1. Build the samples (MSVC, x64 Native Tools Command Prompt for VS 2022)

Use the same commits as the traces.

    mkdir C:\cov & cd C:\cov
    git clone https://github.com/SaschaWillems/Vulkan.git sascha
    cd sascha
    git checkout 41a4410243fca7640a2dd0115a5ff5cb9a29494b
    git submodule update --init              (glm and the assets: about 1 GB)
    cmake -G "Visual Studio 17 2022" -A x64 -S . -B build
    cmake --build build --config Release --target computecloth computenbody bloom
    cd ..

The binaries are `C:\cov\sascha\build\bin\Release\{computecloth,computenbody,bloom}.exe`. The
asset and shader paths are compiled in as absolute paths, so do not move the checkout. Check that
it works with `build\bin\Release\bloom.exe -b -bw 0 -bfs 60`: a window appears, about 60 frames
render, and it exits.

    git clone https://github.com/KhronosGroup/Vulkan-Samples.git khronos
    cd khronos
    git checkout 177edebf0cd7d4f669667e49f052cfb56b17e004
    git submodule update --init --recursive
    cmake -G "Visual Studio 17 2022" -A x64 -S . -B build\windows
    cmake --build build\windows --config Release --target vulkan_samples
    cd ..

The binary is `C:\cov\khronos\build\windows\app\bin\Release\AMD64\vulkan_samples.exe`. Run it from
`C:\cov\khronos`, the working directory that holds `assets\` and `shaders\`. Check that it works
with:

    cd C:\cov\khronos
    build\windows\app\bin\Release\AMD64\vulkan_samples.exe sample afbc --benchmark --hideui --stop-after-frame 60

## 2. Build the layers

MSVC (same prompt):

    cd C:\cov
    cmake -S <path>\covenant\bench\elide\real -B layers-build
    cmake --build layers-build --config Release

This produces `layers-build\layers\Release\`, which holds `VkLayer_COVENANT_elide.dll` and
`VkLayer_COVENANT_probe.dll` with their two `.json` manifests.

MinGW-w64 (UCRT64 shell):

    cmake -S <path>/covenant/bench/elide/real -B layers-mingw -G "MinGW Makefiles"
    cmake --build layers-mingw -j

This produces `layers-mingw\layers\`, which holds `libVkLayer_COVENANT_elide.dll` and
`libVkLayer_COVENANT_probe.dll`. The manifests name the `lib` prefix, and the GCC runtimes are
linked statically.

If the configure step cannot find Vulkan, pass `-DVulkan_INCLUDE_DIR=%VULKAN_SDK%\Include`. The
layers compile against `vulkan/vulkan.h` only and carry their own copy of the `vk_layer.h`
loader-interface structs. On Linux, the same CMakeLists builds with
`cmake -S . -B build && cmake --build build`; this was verified on Linux. The MinGW and
MSVC paths have not been compiled.

## 3. Environment (what measure_real.py sets for each run)

| variable | value |
|---|---|
| `VK_ADD_LAYER_PATH` | the folder with both layer manifests (`;`-separated if more than one) |
| `VK_INSTANCE_LAYERS` | `VK_LAYER_COVENANT_elide;VK_LAYER_KHRONOS_validation;VK_LAYER_COVENANT_probe` (first = closest to the app; drop the ones not in use) |
| `COVENANT_ELIDE_PLAN` | the `.f2.plan.json` |
| `COVENANT_ELIDE_MODE` | `chain` (default). Strict `(recording, index)` keys do not carry across drivers: on lavapipe only 1 of 17 strict keys of the model-driver afbc trace matched |
| `COVENANT_ELIDE_DISABLE=1` | the "off" configuration: layer loaded, plan ignored |
| `COVENANT_ELIDE_STATS` | the layer's JSON counters: recordings, barrier calls, matched, sig_mismatch, removed and narrowed calls |
| `COVENANT_PROBE_TIMESTAMPS` | per-batch TOP/BOTTOM_OF_PIPE timestamps; JSON written at vkDestroyDevice or exit |
| `COVENANT_PROBE_HASH` | FNV-1a 64 hash of every presented image (adds TRANSFER_SRC to the swapchain usage) |
| `COVENANT_PROBE_QUIET=1` | no summary on stderr |
| `VK_LAYER_SETTINGS_PATH` | the `vk_layer_settings.txt` measure_real.py writes for `--validation`: syncval with the shader-access heuristic, log to file |

Hand-run example from cmd, with the plan applied and timestamps on:

    set VK_ADD_LAYER_PATH=C:\cov\layers-build\layers\Release
    set VK_INSTANCE_LAYERS=VK_LAYER_COVENANT_elide;VK_LAYER_COVENANT_probe
    set COVENANT_ELIDE_PLAN=<path>\covenant\bench\elide\real\plans\sw_computecloth.f2.plan.json
    set COVENANT_ELIDE_MODE=chain
    set COVENANT_ELIDE_STATS=%TEMP%\elide.json
    set COVENANT_PROBE_TIMESTAMPS=%TEMP%\ts.json
    C:\cov\sascha\build\bin\Release\computecloth.exe -b -bw 0 -bfs 600
    type %TEMP%\elide.json
    set VK_INSTANCE_LAYERS=

`set VK_LOADER_DEBUG=layer` shows whether the loader found the layers.

On Windows there is no fake clock; it is not needed:

- Sascha `-b` drives `render()` directly with a frozen animation timer, so the images depend only
  on the frame index. This was verified on lavapipe: identical hashes over two runs for bloom and
  computecloth.
- Khronos `--benchmark` forces a fixed 60 fps simulation step.
- `--hideui` removes the fps overlay, which would otherwise change the image.

## 4. Run

From the non-administrator prompt:

    cd <path>\covenant\bench\elide\real
    python measure_real.py ^
        --sw-bin C:\cov\sascha\build\bin\Release ^
        --ks-root C:\cov\khronos --ks-bin C:\cov\khronos\build\windows\app\bin\Release\AMD64\vulkan_samples.exe ^
        --layers C:\cov\layers-build\layers\Release ^
        --frames 1200 --warmup-frames 100 --rounds 10 --validation --out results-gpu

For each sample this:

1. runs base, off and plan once each for 60 frames, hashing every presented image;
2. with `--validation`, runs base and plan once each under syncval (this needs the SDK's
   validation layer on the loader path, which an installed SDK provides);
3. runs 10 rounds of base, off and plan for 1200 frames each, in rotating order, with
   timestamps.

Expect about 1–2 minutes per sample. Use `--samples sw/computecloth,ks/afbc` to run a subset.

The results are `results-gpu\measure_real.json` and the printed table.

### Reading the result

- **GPU busy ms.** For each present interval, this is the sum over submitted batches of the time
  from the TOP_OF_PIPE timestamp to the BOTTOM_OF_PIPE timestamp. The figure is the median over
  frames after warm-up, then the median over runs. The ratios carry a bootstrap 95% CI over runs.
- **Sascha.** The samples also write their own CPU frame times (`-bf` / `-bt`). These are
  recorded as `cpu_frame_ms_median`.
- **Khronos.** The fps that `--benchmark` prints is simulated and is ignored.
- **Hashes.** `hashes equal = False` invalidates the row; report it rather than dropping it.
  Expect them to be equal: the plan changes only one-time barriers, and the
  frame-index-deterministic samples make the images comparable.
- **Layer counters.** In `layer: matched, sig mismatch, ...`, a signature mismatch means the
  program recorded different barriers than in the trace, and the layer passed those barriers
  through unchanged. Expect mismatches on NVIDIA GPUs:
  - NVIDIA's dedicated compute family has index 2, where the model driver used 1, so queue
    family ownership transfer barriers (computenbody, computecloth, compute_nbody) differ;
  - the swapchain image count may differ.

  Both are safe, because those barriers are pinned in the plans anyway.
- **The "plan changes nothing per frame" note.** It comes from the plan's own
  `.report.json`: recordings submitted after the first present. When it is present, a ratio
  different from 1 is noise or layer overhead.
- **async_compute.** It is in the sample list. If its plan is missing (see `real/results/real.md`), the
  script skips it.

## 5. Not verified

These steps have not been verified:

- the MSVC and MinGW compilation of the probe layer: it uses `<windows.h>` only for `__declspec`,
  and the fake-clock lookup is compiled out;
- the samples' Windows builds at these commits.

If the probe layer fails to compile, `measure_real.py` cannot time anything. Fall back to the Sascha
CSV frame times only: remove `VK_LAYER_COVENANT_probe` from the layer list in `run_one`.
